| ADR-007 | 2026-07-19 | События выполнения тренировок, замеров и аудита append-only; офлайн-операции имеют идемпотентный `client_op_id`. | принято | Это снижает конфликтность синхронизации и сохраняет историю для антифрода/аналитики. |
| ADR-008 | 2026-07-19 | Репозиторий разделён на `frontend/` (Nx: PWA и SSR), `backend/` (FastAPI) и `infra/` (Compose/gateway). Frontend feature-библиотеки PWA и showcase не импортируют друг друга; общими служат только разрешённые shared/UI-библиотеки. |
| ADR-009 | 2026-07-19 | Первый контур развёртывания — Tailnet-хост `100.90.138.119`: Nginx/Compose слушает только `127.0.0.1:8080`, доступ предоставляется через Tailscale Serve. PostgreSQL и Redis не публикуют порты на хост; Angular SSR получает явный allowlist корневого домена и поддоменов. | принято | Адрес находится в Tailnet/CGNAT-диапазоне и не используется как публичный DNS-адрес. Публичный домен, внешний ingress, TLS-политика и резервное копирование принимаются отдельным решением до интернет-запуска. Не разрешать SSR принимать произвольный `Host`. |

| ADR-010 | 2026-07-24 | CI выполняется GitHub Actions на PR/push в `main`; CD запускается отдельным HMAC-проверяемым GitHub webhook на production-хосте. Receiver принимает только `push` в `main`, а systemd job делает `git fetch` точного commit, запускает миграции, Compose и health-check. | принято | Исключает хранение SSH-ключа production в GitHub Actions, не использует `git pull` и изолирует публичный webhook от привилегированного deploy job. Доступ сервера к репозиторию — read-only deploy key; секрет webhook и env остаются только на сервере. |
| ADR-011 | 2026-08-13 | Библиотека упражнений принадлежит тренеру; тренировка хранит типизированные упорядоченные блоки и может ссылаться только на упражнения владельца. Медиа на первом шаге задаются проверяемыми `http(s)` URL, загрузка файлов откладывается до защищённого S3-контура. | принято | Не допускает утечки чужих упражнений в тренировку и не создаёт небезопасное файловое хранилище внутри API. Направления/типы блоков не являются DB enum, поэтому могут расширяться миграцией и обновлением контракта. |
| ADR-012 | 2026-08-13 | Пользователь с ролью `client` может явно перейти в роль `trainer` из тренерского сценария. Переход не доступен `admin`, отзывает все активные сессии и выдаёт новую подписанную cookie-сессию. | принято | Устраняет тупиковый сценарий ошибочного выбора клиентской роли без неявного повышения прав или сохранения устаревшего токена. |
| ADR-013 | 2026-08-22 | `BTR-P0-01 v2`: permanent Client footprint возникает только после successful Accept — существование любого `TrainerClientRelationship` (`ACTIVE` или `TERMINATED`) блокирует `CLIENT → TRAINER`. Invitation сама по себе переход не блокирует. Successful BecomeTrainer под Client Account row lock атомарно отменяет все inbound `PENDING` Invitations с reason `CLIENT_ROLE_CHANGED_TO_TRAINER`, затем меняет роль и ротирует сессии одним commit. Accept и BecomeTrainer сериализуются через тот же Client Account lock; lock order остаётся `Account → Invitation → Relationship`. | принято | Уточняет ADR-012 и заменяет v1-семантику ADR-013 до merge P0 foundation. Если Accept выигрывает гонку, Relationship создаётся и BecomeTrainer отвечает `409 BECOME_TRAINER_P0_FOOTPRINT_EXISTS`; если BecomeTrainer выигрывает, Invitation становится `CANCELLED`, Relationship не создаётся, losing Accept получает `409 INVITATION_CANCELLED_BY_ROLE_CHANGE`. История Invitation/Relationship сохраняется; dual-role и role-history не вводятся. |
| ADR-014 | 2026-08-24 | P0 `WorkoutExecution` является singleton-entity для `WorkoutAssignment`: отдельная таблица с `assignment_id UNIQUE`, `started_at` и nullable `completed_at`; физический Execution status не хранится, а логический статус выводится из `completed_at`. Assignment остаётся lifecycle authority и атомарно проходит `PLANNED → IN_PROGRESS → COMPLETED`. Start/Complete идемпотентны через singleton и row locks; общий lock order `Account → Relationship → Assignment → Execution`. | принято | Start разрешён только Client при ACTIVE Relationship; повторный Start возвращает существующий Execution. Уже начатый IN_PROGRESS Execution можно Complete после termination Relationship; повторный Complete возвращает исходный completed Execution без изменения timestamp. Execution не копирует snapshot и не содержит result data; Program/offline/realtime остаются вне P0 scope. |
| ADR-015 | 2026-09-04 | `Workout Results v1` принадлежат конкретному `WorkoutExecution`; identity результата — frozen Assignment coordinates `(block_position, exercise_position, set_index)`, а не `source_exercise_id`. Client единственный mutation actor; partial Results разрешены; Completion возможен без Results; Trainer читает Results только после Completion. PUT — natural-key upsert, DELETE — idempotent; corrections после Completion и termination Relationship разрешены без изменения lifecycle. | принято | Фиксирует уже выпущенную production-архитектуру Results и закрывает пропущенный ADR номер. Planned values никогда не становятся actual автоматически; current Workout не участвует в historical mapping; History остаётся отдельной read projection и не встраивает Results. |
| ADR-016 | 2026-09-06 | `Training Programs v1` эволюционирует существующий mutable `Program`: public field `duration_weeks`, live `ProgramSlot` schedule и full replacement update. Issuance создаёт отдельный immutable `ProgramAssignment` с frozen Program snapshot (schedule + Workout IDs, без Workout content) и атомарно материализует ordinary child `WorkoutAssignment` rows с собственными frozen Workout snapshots. Child provenance — nullable `program_assignment_id` FK и immutable copied `program_slot_id` без FK на live slot. | принято | Один parent `request_id` идемпотентно защищает всю issuance; retry возвращает original issuance даже после Program edit. Все slots создаются одним commit через shared commit-free Assignment materializer. Program edit/assign сериализуются Program row lock; Program cancellation отменяет только `PLANNED` children, а Start race сериализуется через Relationship lock. IN_PROGRESS/COMPLETED/Results/History и Direct Assignment semantics остаются прежними; Program Sync, parent auto-complete и отдельный execution engine не вводятся. |

## Как добавлять ADR

1. Сначала записать предложение и статус «на утверждении».
2. После подтверждения сменить статус на «принято» или «отклонено»; не переписывать историю.
3. Если решение меняется, добавить новую строку с ссылкой на заменяемый ADR.
