# HLS-поток для новых видео упражнений

**Статус:** дизайн утверждён владельцем 2026-09-24.  
**Область:** только новые private-видео упражнений; существующие MP4 не мигрируются.

## Цель и критерии приёмки

Клиент должен начинать воспроизведение и перематывать новое видео упражнения без скачивания всего исходного файла. При перемотке браузер получает только ближайшие HLS-сегменты. Доступ остаётся private: тренер видит только своё видео, а клиент — только медиа, зафиксированное в его immutable workout snapshot и доступное при активной связи.

Успех:

- новое видео преобразуется в один HLS-вариант не выше 720p с сегментами около двух секунд;
- перемотка запрашивает новый небольшой сегмент, а не исходный MP4;
- исходник, manifest и сегменты никогда не становятся публичными;
- упражнение нельзя сохранить с новым видео до готовности потока и обложки;
- старые упражнения продолжают воспроизводить текущий private MP4.

Не входит в этот выпуск: обработка уже загруженных видео, несколько качеств/ABR, CDN signed cookies, аналитика просмотра и ручной выбор качества.

## Архитектура и данные

`media` остаётся владельцем исходного объекта и производного потока. После подтверждения нового `EXERCISE_VIDEO` создаётся одна запись `exercise_video_streams`, связанная с source `media_id` one-to-one:

- `status`: `PENDING`, `PROCESSING`, `READY`, `FAILED`;
- `manifest_key`, `segment_prefix`, `duration_seconds` после успешной обработки;
- `attempt_count`, `last_error_code`, `started_at`, `completed_at` для повторов и наблюдаемости.

Исходный объект хранится как private `exercise-video/...`; HLS-артефакты — как private `exercise-hls/{media_id}/...`. Они принадлежат тому же source media ID, поэтому snapshots по-прежнему фиксируют один неизменяемый идентификатор. Готовый поток нельзя заменить или изменить без нового video media ID.

Новый сервис Compose `video-worker` запускается из образа backend и имеет FFmpeg. Он опрашивает durable записи `PENDING`/retry, захватывает одну задачу через транзакцию с `FOR UPDATE SKIP LOCKED`, скачивает исходник во временную директорию, создаёт fMP4 HLS и выгружает артефакты в S3. Воркер обрабатывает одну задачу одновременно; его временные файлы удаляются в `finally`. Ошибка повторяется с ограниченным числом попыток, затем фиксируется как `FAILED` без раскрытия системной ошибки клиенту.

FFmpeg-профиль: H.264/AAC, `yuv420p`, максимум 1280px по длинной стороне, GOP около двух секунд, fMP4 segments около двух секунд и один variant playlist. Он намеренно не создаёт несколько качеств в первой версии.

## Доступ и API

API не отдаёт публичную ссылку на manifest. После текущей проверки владельца или assignment snapshot он выдаёт endpoint manifest:

- trainer: `GET /exercises/{exercise_id}/video/stream.m3u8`;
- client: `GET /workout-assignments/{assignment_id}/exercise-media/{media_id}/stream.m3u8`.

Endpoint читает private playlist из S3 и перед отправкой подставляет абсолютные signed GET URLs на каждый сегмент. Подписи живут ограниченное время (15 минут) и содержат только один сегмент. Сам manifest отправляется с `application/vnd.apple.mpegurl` и `Cache-Control: no-store`.

Клиентский assignment endpoint применяет существующую проверку active relationship и frozen snapshot до чтения любого manifest. Для source media, не принадлежащего упражнению snapshot, он отвечает как текущий media endpoint. В случае истечения подписи HLS-плеер один раз обновляет manifest через авторизованный API и повторяет сегмент.

`ExerciseResponse` получает состояние потока; upload/confirm response сообщает, что видео обрабатывается. Существующий MP4 read URL остаётся только fallback для legacy media без готовой HLS-записи.

## Интерфейс

После загрузки исходного файла и автосоздания обложки редактор показывает «Обрабатываем видео…» и блокирует «Сохранить». При `READY` отображается обычное «Видео и обложка готовы». При `FAILED` интерфейс объясняет, что видео не обработалось, и предлагает повторить обработку без повторной загрузки; после исчерпания попыток можно выбрать другой файл.

Плеер выбирает HLS для `READY` stream. Safari использует native HLS; остальные поддерживаемые браузеры используют `hls.js` с запросами manifest через текущую cookie-сессию. Poster остаётся private thumbnail. Legacy private MP4 и URL-based legacy exercises не меняют текущего поведения.

## Ошибки, безопасность и эксплуатация

- API и worker никогда не доверяют имени/плейлисту от пользователя: manifest создаёт FFmpeg, ключи S3 формирует backend.
- Bucket остаётся private. CORS разрешает production PWA только `GET`, `HEAD`, `PUT`; для диагностики streaming также expose `Content-Range` и `Accept-Ranges`.
- Worker не запускает пользовательские аргументы и ограничивает вход существующим типом/размером media policy. Временный каталог не сохраняется после job.
- При рестарте worker застрявшая задача возвращается в retry по time lease; сервисные логи и метрики отражают `READY`, `FAILED`, длительность обработки и число попыток без URL и секретов.
- Compose задаёт worker ограничение в одну параллельную обработку, чтобы не ухудшать API/PWA на текущем production-host.

## Тестирование и выпуск

Unit/integration-тесты покрывают создание stream job при confirm, транзакционный захват/retry, отказ в чтении manifest без ownership/snapshot, подстановку signed segment URLs, запрещённое сохранение во время processing и fallback старого MP4. Frontend-тесты покрывают выбор HLS/native playback и состояния editor.

Перед выпуском: migration на тестовой PostgreSQL, worker с тестовым коротким MP4, проверка `206` для сегмента, попытка доступа другого тренера/клиента, ручная перемотка в Chrome и Safari, health API/PWA/worker. Никакие существующие медиа не переобрабатываются.
